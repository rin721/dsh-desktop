# 上游兼容 Windows 桌面应用需求

[English](requirements.md) | 中文

## 目标

交付具备桌面产品品质的 DeepSeek Harness Windows 发行版，其常规更新路径直接使用官方上游发布物，不编辑、不复制 Harness 核心，也不维护 Harness 核心分叉。

应用必须具备已安装桌面产品的体验，同时保留现有 Web 客户端和 Harness 运行时作为产品实现。因此，“桌面”指原生安装、窗口、生命周期、系统集成、诊断和发布管理，而不是用原生 UI 工具包重写 React 界面。

## 范围内

1. 建立独立版本的桌面伴生仓库，负责 Electron 代码、Windows 安装器、内置 Node.js 运行时、更新自动化和桌面专用测试。
2. 把官方 `@deepseek-ai/dsh` npm 发布物作为主要上游供应路径，并使用精确版本和锁文件固定依赖。
3. 使用独立 Node.js 子进程在环回地址和自动分配端口上运行 `dsh web`，使 Harness 原生依赖不受 Electron ABI 影响。
4. 使用加固的 Electron 窗口加载受监管的本地 Harness 服务，并阻止非预期导航、弹窗、权限请求和渲染进程访问 Node.js。
5. 实现桌面生命周期行为，包括单实例激活、启动反馈、干净关闭、不包含秘密的崩溃报告，以及防止遗留孤儿子进程。
6. 交付签名且自包含的 Windows x64 安装器，不要求用户另行安装 Node.js、pnpm 或浏览器扩展。
7. 建立可重复的上游更新流程，包含兼容性门禁、发布元数据、回滚，以及桌面外壳版本和内置 Harness 版本的独立展示。
8. 可选地提交一个独立评审的上游贡献，通过极小 CLI 层修改提供稳定的机器可读就绪和优雅关闭契约。

## 约束

| ID | 约束 |
| --- | --- |
| C-001 | 主路线不得修改 DeepSeek Harness 源码检出中的文件，也不得在常规构建中应用源码补丁。 |
| C-002 | 上游代码必须通过可追溯的官方包发布物和冻结的依赖锁进入产品；从源码标签或提交构建是有文档记录的备用方案，而不是默认方案。 |
| C-003 | 初始支持目标是 64 位 Windows 10 和 Windows 11；Windows ARM64、macOS 和 Linux 打包需要单独验收。 |
| C-004 | 打包后的运行时必须仅绑定 `127.0.0.1`、申请临时端口，并且默认不得把 Harness 暴露到局域网接口。 |
| C-005 | 渲染进程必须使用 `nodeIntegration: false`、`contextIsolation: true` 和 `sandbox: true`，且不得提供通用 preload 桥接。 |
| C-006 | 必须保留默认 `$DSH_HOME` 或 `~/.dsh` 行为，使 CLI、Web 和桌面入口共享用户状态，除非用户明确覆盖。 |
| C-007 | 当执行或合规要求时，运行时二进制、原生模块、声明和许可证必须保持可检查，并在 `app.asar` 外打包。 |
| C-008 | 更新任务必须验证包完整性、从已提交锁文件可重复构建，并在缺少兼容性、签名或冒烟测试证据时以失败关闭。 |
| C-009 | 日志和诊断必须隐去凭据、令牌、环境秘密和 `$DSH_HOME` 下的敏感内容。 |
| C-010 | 应用实施、依赖安装、签名、发布和任何上游拉取请求，都必须在本计划评审后获得明确确认。 |

## 非目标

1. 使用 WPF、WinUI、Qt、Flutter 或其他原生 UI 框架重写现有 React 客户端。
2. 在首个版本中用 Electron IPC 替换当前 HTTP 和 WebSocket 传输。
3. 在 Electron 主进程或渲染进程内加载完整 Harness 运行时。
4. 把长期分叉、复制的源码树或静默补丁栈作为常规更新模型。
5. 添加新的 Harness 产品能力、改变智能体行为或重新设计现有 Web 页面。
6. 在首个版本中交付后台 Windows 服务、多用户计算机安装、Microsoft Store 包或企业 MSI。
7. 在签名安装器升级和回滚尚未通过人工验证前，实现应用内自动更新。
8. 仅因去掉浏览器外框就宣称获得原生桌面隔离；首个版本有意保持为桌面外壳内的本地 Web 应用。

## 验收标准

| ID | 标准 | 必需证据 |
| --- | --- | --- |
| AC-001 | 干净的桌面构建使用精确版本的官方 `@deepseek-ai/dsh`，不编辑或修补上游检出。 | 依赖清单、冻结锁文件、干净的上游 `git status` 和构建日志。 |
| AC-002 | 在未另行安装 Node.js 或 pnpm 的全新受支持 Windows x64 虚拟机上，安装和首次启动成功。 | 记录的干净虚拟机安装与启动测试。 |
| AC-003 | 启动时只打开一个独立应用窗口，不打开默认浏览器、不显示控制台窗口，第二次启动会重新聚焦已有窗口。 | 自动化单实例测试和屏幕录像或截图。 |
| AC-004 | 受监管的 Harness 进程在临时端口上绑定 `127.0.0.1`，并通过机器校验的就绪信号获知所选 URL。 | 集成日志和套接字检查。 |
| AC-005 | 正常关闭窗口会请求有界优雅关闭，且不遗留 Harness 或内置 Node.js 进程；崩溃和强制关闭路径也会清理后代进程。 | 覆盖正常关闭、启动失败、子进程崩溃和父进程崩溃的生命周期集成测试。 |
| AC-006 | 打包后的客户端完成现有 Web 启动路径、打开会话、交换流式响应、重新加载，并保留预期的 `$DSH_HOME` 状态。 | 使用隔离测试主目录的打包端到端测试。 |
| AC-007 | 渲染进程安全设置、导航限制、弹窗处理、权限拒绝、内容安全策略和环回来源检查通过自动化断言。 | 安全测试报告和经检查的 Electron 配置。 |
| AC-008 | 生产发布的安装器和应用可执行文件完成签名、包含第三方声明，并且发布门禁中没有非预期 SmartScreen 或杀毒软件发现。 | 签名验证、声明清单和发布扫描结果。 |
| AC-009 | 关于和诊断视图展示桌面外壳版本、精确内置 Harness 版本、Node.js 版本和构建标识，且不暴露秘密。 | UI 截图和诊断快照测试。 |
| AC-010 | 上游版本升级作为可评审的依赖更新变更执行，从冻结锁文件重新构建，并运行单元、生命周期、打包端到端和安装器冒烟门禁。 | 成功的更新拉取请求和附带的门禁结果。 |
| AC-011 | 失败的上游兼容性门禁不能替换最后一个已知良好的桌面版本，并保留上一版签名安装器用于回滚。 | 失败候选演练和回滚记录。 |
| AC-012 | 启动、就绪和关闭失败时显示可操作的桌面错误页，其中包含安全日志位置以及重试或退出操作，而不是空白窗口。 | 故障注入截图和测试。 |
| AC-013 | 兼容性监管适配器隔离在版本化的桌面自有接口之后，使已被接受的上游监管协议可以替换它，而无需修改窗口或打包代码。 | 接口测试和依赖图评审。 |
| AC-014 | 仅在实施交付后更新 Harness 当前状态文档，并通过仓库 Agent Note 流程记录实施决策。 | 文档差异、链接检查和已接受的 Agent Note。 |
